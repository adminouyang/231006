# IPTV 直播源检测脚本

拉取远程订阅（txt / m3u）→ 校正频道名 → 过滤黑名单 → 多线程测速 → 输出 ipv4 / ipv6 两份 txt + m3u，并写检测日志。

## 目录结构

```
py/TV/
├─ main.py                  # 入口
├─ requirements.txt
├─ tvcheck/
│  ├─ settings.py           # 配置与命令行参数
│  ├─ sources.py            # 订阅拉取、txt/m3u 解析、IPv4/IPv6 判定
│  ├─ names.py              # demo.txt 别名校正、分组归属、排序
│  ├─ resolution.py         # 分辨率档位与对应速度阈值
│  ├─ videoprobe.py         # 从码流(TS/H.264/HEVC SPS)探测真实分辨率
│  ├─ blacklist.py          # 失效主机黑名单（只认 HTTP 状态码）
│  ├─ speedtest.py          # 各种源的测速实现
│  ├─ writer.py             # txt / m3u / sort.log 输出
│  ├─ selftest.py           # 离线自检
│  └─ models.py
├─ config/
│  ├─ subscribe.txt         # 远程订阅链接，一行一个
│  ├─ demo.txt              # 频道名校正表（主名|别名1|别名2|）
│  ├─ blacklist.txt         # 失效域名 / IP:端口（脚本自动维护）
│  └─ local.txt             # 本地源，不测速，只改名后合并
└─ output/
   ├─ ipv4/tv.txt, tv.m3u
   ├─ ipv6/tv.txt, tv.m3u
   └─ sort.log
```

## 运行

```bash
pip install -r py/TV/requirements.txt
python py/TV/main.py
```

常用参数：

| 参数 | 说明 | 默认 |
| --- | --- | --- |
| `--workers N` | 并发线程数 | 96 |
| `--threshold N` | 强制统一速度阈值 KB/s（覆盖分辨率阈值与码率基准） | 不启用 |
| `--timeout N` | 单源总耗时上限（秒） | 20 |
| `--max-per-channel N` | 每个频道保留地址数 | 6 |
| `--verify` | 校验 HTTPS 证书 | 关闭 |
| `--keep-non-http` | 保留 rtmp/rtsp 等源 | 关闭 |
| `--no-local` | 不合并 local.txt | 合并 |
| `--skip-test` | 跳过测速，只改名合并 | 关闭 |
| `--self-test` | 离线自检（不联网，验证解析/改名/输出/判定口径） | 关闭 |
| `--limit N` | 只跑前 N 个订阅源（调试） | 0 |
| `--warmup N` | 慢启动预热秒数，不计入速度；`0` 表示不剔除 | 1.0 |
| `--bitrate-margin N` | 码率冗余系数 | 1.35 |
| `--floor N` | 最低速度要求 KB/s | 100 |
| `--bitrate-strict` | 完全按流码率判定（高码率源也会被收紧） | 关闭 |
| `--no-retest` | 只跑一轮，不做临界源重测 | 重测 |
| `--strict` | 回到旧的单轮判定（不剔慢启动、不按码率放宽、不重测） | 关闭 |
| `-v` | 输出更多过程信息 | — |

## 配置文件

### config/subscribe.txt
一行一个订阅链接，`#` 开头为注释。GitHub 链接会自动尝试 `gh-proxy.com` / `ghfast.top` / `gh.catmak.name` 等加速镜像；txt 与 m3u 按内容自动识别（不依赖后缀）。

### config/demo.txt（频道模板）
用 `分组,#genre#` 声明分组，用 `主频道名|别名1|别名2|` 声明别名。

**输出完全按这个模板走**：

- 命中别名的频道 → 用主名输出，并放进主名所处的分组；
- 没命中的频道 → 名称保持原样（只去掉“高清/超清/HD”等画质后缀），**统一归入模板里的兜底分组**（`其它` / `其他` / `其它频道` / `其他频道`，取模板中已有的那个，都没有才新建 `其它频道`）；
- 分组顺序、组内频道顺序都按模板走，不会因为源里的顺序而变；
- 源里自带的 `group-title` / `#genre#` 分组不参与输出分组，模板里没有的分组不会出现在结果里。

匹配时会忽略大小写、空格、横杠、括号与画质后缀，所以 `CCTV-1 综合 高清` 也能对上 `CCTV1`。

### 分辨率与速度阈值
每个源按分辨率档位取阈值，而不是固定 300KB/s：

| 档位 | 8K | 4K | 1080p | 720p | 576p | 540p | 480p | 360p | unknown |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 阈值 KB/s | 2048 | 1900 | 465 | 282 | 144 | 130 | 125 | 60 | 1024 |

档位判定优先级：

1. HLS 主播放列表里的 `RESOLUTION=1920x1080`（直接来自源）；
2. 码流本身：解析 TS 的 PAT/PMT 找到视频 PID，再解 H.264 `SPS`(NAL 7) / HEVC `SPS`(NAL 33) 得到真实宽高（含 frame_cropping），单码率 m3u8 分片和直连 ts 都走这条；
3. 频道名里的线索：`8K/4K/2160P/1080P/720P/576P/540P/480P/360P`，以及 `超高清→4K`、`超清/蓝光→1080p`、`高清→720p`、`标清→576p`；
4. 都没拿到 → `unknown`（1024KB/s）。

> 极少数流（加密/私有封装、或前 64KB 内没有关键帧）探不出分辨率，会落到 `unknown`，门槛较高。

### 判定基准：为什么「能流畅播放却测不出」

单纯拿上表当门槛会误杀大量实际能播的源，四个原因叠加：

| 原因 | 表现 | 处理 |
| --- | --- | --- |
| 短窗口含 TCP 慢启动 | 1 秒窗口里平均速度只有稳态的一半 | 记录采样点，**剔除前 1 秒**，只算稳态速度 |
| 判定基准错位 | 480p 源码率 300KB/s，却要求 1024KB/s | 用**流自身码率 × 1.35** 作为目标，与档位阈值取较宽松者 |
| 96 并发自己抢带宽 | 每条只分到出口带宽的零头 | 临界源**低并发重测**（8 线程）补一次 |
| 单次测量无容错 | 源在波动，一次不达标就淘汰 | 重测取两次的最好成绩 |

码率从哪来：媒体播放列表的 `#EXTINF` 时长 + 分片的 `Content-Length`，所以不必把整个分片下完就能算出 `字节/时长`；主播放列表则退回用 `BANDWIDTH` 声明值。

判定目标是 `min(档位阈值, max(码率×1.35, 100KB/s, 档位阈值×0.2))`：

- 只放宽、不收紧——不会因为码率算出来偏高而淘汰原本达标的源；
- 三重下限挡住「错误码率把门槛放太松」，也挡住极低码率的劣质源；
- 想双向精确判定（高码率源也按真实需求收紧）用 `--bitrate-strict`；
- 完全不想用这套逻辑，`--strict` 回到旧的单轮判定。

> 想让结果更宽或更严，优先调 `--bitrate-margin`（1.2 更松 / 1.6 更严）和 `--floor`。
> 宽严程度直接影响输出列表长度：越松，可用地址越多，但个别源可能偶发卡顿。

### config/blacklist.txt
脚本自动维护，格式 `host:port,失败次数,最后失败时间,原因`。

**只有「服务端返回错误状态码」的源才会入库**，判定依据仅此一条：

- 入黑名单的条件：最后一次请求返回 `4xx / 5xx`（`408`、`425`、`429` 属于临时抖动，不算）；
- 超时、连不上、速度不达标、返回网页内容 —— 一律**不**记录；
- 同一 `host:port` 累计出现 3 次状态码错误才真正跳过；
- 记录超过 7 天自动失效并重新尝试；
- 检测成功会移除记录；
- 也可手工写 `1.2.3.4:8080` 或 `example.com`（代表该主机全部端口）强制跳过。

### config/local.txt
本地源，不参与测速，只做频道名校正后合并进输出。格式与远程 txt 一致（也支持 m3u）。

## 输出

- `output/ipv4/tv.txt`：`分组名,#genre#` + `频道名,url`，同一频道多行
- `output/ipv4/tv.m3u`：带 `x-tvg-url`(EPG)、`tvg-name`、`tvg-logo`、`group-title`，台标取自 `https://codeberg.org/ou-yang/TV/raw/branch/main/LOGO/{频道名}.png`
- `output/ipv6/*`：同上，只放 IPv6 源
- `output/sort.log`：每轮覆盖，表头是阈值表与判定口径，逐条记录 `分辨率 / 判定依据 / 速度 / 均速 / 阈值 / 数据量 / 总耗时`，末尾是统计与重测结果

## 测速怎么做的

不同源的形态差异很大，脚本按响应内容分流：

1. **HLS（.m3u8）**：先读播放列表；如果是多清晰度主列表，按 `BANDWIDTH` 从高到低挑变体，并顺手取该变体的 `RESOLUTION` 作为分辨率档位；再顺序下载最多 4 个分片累计字节数，同时用 `#EXTINF` 时长与分片 `Content-Length` 算流码率。只测播放列表文件本身会得到假速度，所以必须落到分片。
2. **直连流（.ts / .flv / .mp4 / mp3 等）**：最多读 `3MB`，或攒够 `768KB` 且测速窗口 ≥2.5s 就提前收手，按首包到末包的实际耗时算吞吐。
3. **伪装成网页的错误页**（返回 HTML / JSON）：直接判失败，避免误判为“有速度”。
4. **非 HTTP 协议**（rtmp / rtsp / udp / p2p …）：默认丢弃，`--keep-non-http` 可保留但不测速。
5. **反爬 / 防盗链**：依次尝试 Chrome UA、okhttp UA、带 Referer 的请求；HTTPS 自签证书会二次以 `verify=False` 重试。

速度 = 累计字节 ÷ 数据接收时间窗，且**剔除前 1 秒的慢启动阶段**（窗口短于 1.4 秒时无法剔除，退回平均速度）；数据量不足 20KB 视为无效流。测出的速度与判定目标比较，达到才输出。同一 host 最多 6 个并发，且排队时按 host 轮转，避免一台服务器的几十个频道把线程占满。

首轮跑完后，速度落在目标 60%~100% 之间的「临界源」会和「疑似被自己人挤超时」的源一起，用 8 个线程低并发重测一次，取最好成绩——这是把「能播却测不出」捞回来的主要手段。

## GitHub Actions

`.github/workflows/tv-check.yml` 每天定时运行，跑完自动提交 `py/TV/output` 与 `blacklist.txt`，并把 `sort.log` 作为 artifact 上传。

> 注意：GitHub 的 Ubuntu runner 默认没有 IPv6 出口，IPv6 源在 CI 上大概率全部测速失败。IPv6 结果建议在本机（有 IPv6 网络的环境）执行 `python py/TV/main.py` 生成。
